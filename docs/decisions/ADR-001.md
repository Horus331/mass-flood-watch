# ADR-001: Three compute tiers, all free (Sentinel, Engine, Fallback)

Status: accepted 9 Nov 2026 (master prompt); partly built. Last reviewed 11 Nov 2026.

## Context
The system must run live, unattended and at $0. Storm watching is light and frequent; the flood model is heavy and needs GPUs.

## Decision
1. **Sentinel on GitHub Actions** (public repo, free runners): `sentinel.yml` every ~10 min sets QUIET / WATCH / ACTIVE in
   `docs/site/data/status.json` (rules: `docs/proto/live/SENTINEL.md`). Concurrency groups keep runs from overlapping.
2. **Engine on WPI Turing** (Slurm, GPUs): flood-model ensembles, hindcasts, surrogate training. Turing cannot receive webhooks, so it pulls
   work: today `proto/turing/queue_runner.slurm` (1 CPU, 2 GB, seconds per run) re-submits itself every 30 min and reads `jobs.json` on the
   `turing-queue` branch. Every GPU job is split into a GPU solve and a CPU post-processing job, so no GPU is ever held idle.
3. **Fallback on Actions (CPU)**: the current forecast (`forecast.yml`, LISFLOOD-FP on CPU, four 20 km boxes) and, later, the surrogate.

## Alternatives
Paid cloud GPUs (rejected: cost); everything on Actions (rejected: 6 h job limit, no GPU, abuse-review risk at high volume).

## Consequences
- GitHub cron runs late; `keeper.yml` re-dispatches overdue live workflows.
- The recurring Turing poller and pushes from compute nodes are pending WPI ARC's answer (email drafted 9 Nov; Mo decided 10 Nov to keep
  the poller running meanwhile).
- Not built yet: what each state starts (WATCH pre-stage, ACTIVE full ensemble), the surrogate, the "fallback mode" banner.
